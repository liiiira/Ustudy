# 04 — User Domain

This is a domain-level look at the `User` aggregate — invariants, identity,
and access control — rather than a restatement of the route table (that's
one HTTP-layer view of the domain and lives with the API surface itself).

## Identity and invariants

A `User` is identified by a server-generated UUID, not by `email` or
`username` — those are unique, mutable attributes, not identity. Two
invariants are enforced at the service layer before any write reaches the
repository:

- **Email uniqueness** — checked on both `create` and `update` (only when the
  email actually changes, avoiding a needless lookup on unrelated updates).
- **Username uniqueness** — same pattern.

These are business rules, not just storage constraints — the service layer
is what turns "insert conflict" into a meaningful `409 Email Already Exists`
before the write is even attempted, rather than letting a raw DB constraint
violation leak upward as an opaque error. (A unique index on `email`/`username`
at the schema level would still be worth adding as defense in depth against a
race between the check and the write — see below.)

## Password handling

Passwords are hashed with bcrypt before being persisted — a one-way,
salted, computationally expensive hash function, chosen specifically so that
a database compromise doesn't directly expose reversible credentials (unlike
encryption, hashing here is deliberately one-directional: there's no `decrypt`
operation, only `compare`). The service layer is the only place a plaintext
password exists outside of the request body itself; the repository layer
never sees it.

## Partial updates

`PATCH /users/:id` follows partial-update semantics (RFC 5789): only fields
present in the request body are considered for modification, and each
changed field is diffed against the current value before being included in
the write — if nothing actually changed, the service returns `null` and the
controller responds `204 No Content` rather than issuing a no-op `UPDATE`.

## Authorization model (in progress)

The posts and comments domains already enforce ownership at the service layer
(`userId !== ownerId` before a mutation is allowed) — the same pattern is
being extended to the user domain next: `isAuthenticated` on the
single-resource and mutating routes, plus a matching ownership check in
`user.service` so a caller can only ever modify their own record. Until that
lands, those routes are intentionally excluded from the auth rollout rather
than finished.

## Future Plans

- **Finish wiring `isAuthenticated` and ownership checks** on the
  single-resource and mutating user routes, mirroring the pattern already
  used by `post.service`/`comment.service` — top of the list for this
  domain.
- **Role-based access control.** There's currently no `role`/permission
  concept on `User` — "is this the resource owner" is the only authorization
  primitive modeled so far. Community moderation and any admin surface will
  need a role model on top of that.
- **Database-level uniqueness constraints** on `email` and `username` as a
  second line of defense against the check-then-insert race the
  service-layer check alone doesn't close (two concurrent registrations for
  the same email can both pass the `SELECT` check before either `INSERT`
  commits).
- **Input normalization.** Email is stored as received — no case-folding —
  so `A@x.com` and `a@x.com` would currently be treated as distinct,
  undermining the uniqueness invariant this document just described.
- **Pagination on `GET /users`.** Returns the entire table unbounded; fine at
  current scale, a liability once the user base grows.
