# 05 — Authentication

## Overview

A stateless, bearer-token authentication system built from scratch (no
third-party identity provider), following the **access token / refresh
token** split common to OAuth2-inspired architectures. The goal: keep
per-request authorization a pure, stateless JWT verification (no DB round
trip to check "is this user logged in"), while still retaining server-side
control over session lifetime through the refresh token, which *is* backed by
a database record and therefore revocable.

## Token model

| Token | Lifetime | Purpose | Transport | Revocable |
|---|---|---|---|---|
| Access token | 15 min | Authorizes requests to protected endpoints | `Authorization: Bearer <token>` header | No — stateless JWT, valid until signature/expiry check fails |
| Refresh token | 7 days | Mints new access tokens | `httpOnly`, `sameSite: strict` cookie, sent only to `/refresh` | Yes — validated against a database record on every use |

The short access-token lifetime bounds the blast radius of a leaked token
(e.g. via XSS); the longer refresh-token lifetime keeps the user session
alive without re-authentication, at the cost of needing that one piece of
server-side state. This is the standard tradeoff the access/refresh split
exists to make explicit rather than avoid.

## Backend mechanics

- **`isAuthenticated` middleware** verifies the bearer JWT's signature and
  expiry and attaches the decoded subject (`req.user = { id }`) to the
  request — a pure function of the token, no database dependency, which is
  what keeps authorization checks cheap on every protected route.
- **`/refresh`** decouples two independent questions: "is this JWT
  well-formed and unexpired" (signature/expiry check, stateless) from "has
  this specific session been revoked" (a DB lookup by user id, checking
  `revoked_at`/`expires_at` against the stored, hashed token). Both must pass
  before a new access token is minted.
- **Refresh tokens are stored hashed (SHA-256), not raw.** The database never
  holds a usable token — only a hash of it — so a leak of the `refresh_tokens`
  table alone (without also leaking the still-live JWT `REFRESH_SECRET` and an
  intercepted token) doesn't hand an attacker a working session. Verification
  hashes the incoming token and compares against the stored hash with a
  constant-time comparison (`crypto.timingSafeEqual`), avoiding a timing side
  channel on the comparison itself.
- **Logout** revokes the refresh token's database record. Because access
  tokens are stateless and not individually revocable, logout guarantees the
  session cannot be *renewed* past that point — it does not retroactively
  invalidate an access token already in flight, which remains valid for up to
  its remaining ≤15-minute lifetime. This is a direct, known consequence of
  choosing stateless access tokens, not an oversight.
- **Session model is currently 1:1 (user → refresh token)**, enforced by a
  unique constraint plus an upsert-on-conflict at the repository layer — a
  deliberate MVP simplification, not a multi-device session model. See
  "Things to add."

## Frontend mechanics

- **`token.ts`** encapsulates access-token storage behind `get`/`set`
  functions rather than exposing a shared mutable module-level variable —
  the token's lifecycle has exactly one owner, so the storage strategy
  (in-memory today) can change without touching every call site.
- **Transparent refresh on `401`.** The fetch layer intercepts a `401`,
  calls `/refresh`, retries the original request once with the new access
  token, and only surfaces a failure (and logs the user out client-side) if
  the refresh itself fails — the retry is bounded to a single attempt, not a
  loop.
- **`AuthContext`** centralizes `isAuthenticated`/`loading`/`login`/`logout`
  as shared state via React's Context API, so auth state has one source of
  truth in the component tree instead of being re-derived or prop-drilled
  per component.
- **`ProtectedRoute`** redirects unauthenticated access to `/login` using
  `navigate(..., { replace: true })` — replacing rather than pushing the
  history entry, so a back-navigation after redirect can't land back on a
  route that was never actually authorized.

## Request lifecycle

```
1. Login          → server issues access + refresh token; refresh token persisted (hashed) server-side.
2. Authorized call → client attaches access token as a bearer credential.
3. Access expires  → request returns 401.
4. Refresh         → client calls /refresh; server validates the DB-backed refresh token; issues a new access token; original request retried once.
5. Logout          → refresh token's DB record revoked; client clears local auth state.
```

## Future Plans

- **Per-(user, device) refresh tokens.** Move from one refresh token per user
  to one per session/device, enabling true concurrent multi-device login and
  *selective* revocation ("log out this device" without affecting others).
  This is also the prerequisite for refresh-token rotation with reuse
  detection: issuing a new refresh token on every use and flagging a replay
  of an already-rotated token as a compromise signal.
- **Email verification at registration.** Account creation isn't currently
  gated on proof of email ownership.
- **OAuth2 / OIDC social login.** Add third-party identity providers (Google,
  etc.) via the authorization-code flow, issuing UStudy's own access/refresh
  tokens once the provider's identity assertion is verified — this keeps the
  rest of the system's authorization model (UStudy-issued JWTs) unchanged
  regardless of how identity was established.
- **Rate limiting on `/login` and `/refresh`.** No throttling currently
  exists on authentication endpoints — a natural fit for Redis (see
  `00-project-setup.md`), which was reserved for exactly this kind of
  ephemeral, high-write-volume state.
- **`secure: false` on the refresh-token cookie is explicitly a
  local-development setting** in the current code and needs to become
  environment-conditional (`true` outside local dev) before any non-local
  deployment — flagged here so it isn't lost.
