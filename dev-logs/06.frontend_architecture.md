# 06 — Frontend Architecture

## Layering

The frontend mirrors the backend's feature split rather than organizing by
technical layer first: `features/{auth,users,posts,comments,communities}`,
each holding its own `api/`, `components/`, `hooks/`, and (where relevant)
`pages/`/`context/`. A change to one domain — say, comments — stays inside
`features/comments/`; it doesn't ripple across a global `components/` or
`services/` folder shared by every feature. This is the same **Single
Responsibility**-at-the-module-level argument made for the backend's layering
in `02.backend_architecture.md`, applied to a client instead of a server.

```
api/          thin wrapper functions over the shared fetch client
hooks/        one data-fetching hook per resource (use<X>, use<X>List)
components/   presentational + form components
pages/        route-level composition of the above
types.ts      DTOs + component prop types for the feature
```

## The fetch client as an adapter layer

`lib/api.ts` exposes exactly two entry points — `publicFetch` (unauthenticated)
and `authFetch` (attaches the bearer access token, and on a `401`
transparently refreshes and retries once) — and every feature's `api/*.api.ts`
funnels through one of them. This plays the same role client-side that the
backend's repository layer plays server-side: it's the one place that knows
about the transport (`fetch`, headers, the `{status, message, <entity>}`
response envelope), so the rest of the app works with plain DTOs instead of
raw HTTP concerns. Query-string construction is factored into its own unit
(`utils/concatQueryParams.ts`) rather than inlined, keeping the transport
adapter itself focused on request/response shape.

## Hooks as the client-side data-access boundary

Each domain exposes a `use<Resource>`/`use<Resource>List` hook
(`useProfile`, `usePosts`, `usePost`, `useComments`, `useCommunitiesList`,
`useCommunity`) with a consistent shape: a `useEffect` fetch on mount/dependency
change, and a `{ loading, error, data }` result. Components never call
`api.ts` functions directly — they consume a hook, the same way a service
never talks to raw SQL directly on the backend. This is the natural next
abstraction to formalize (see "Future Plans") once enough of these hooks
share the same caching/retry needs.

## Session lifecycle

`AuthContext` (React Context) is the one piece of cross-cutting client
state — everything else is local to the component or hook that owns it, a
deliberate choice to avoid reaching for a state-management library before
the app's actual complexity calls for one. `AuthProvider` restores a session
on cold start (mount-time `refresh` + `getMe`, `loading` gating render until
that resolves) rather than assuming logged-out until an explicit `login()`
call — full detail in `05.authentification.md`'s "Frontend mechanics."

## Route guarding

`react-router`'s nested-route model is used directly for access control:
`ProtectedRoute` is a pathless parent `<Route>` wrapping every authenticated
route, so guarding is declared once in the route tree rather than checked
per page — the client-side equivalent of the backend's `isAuthenticated`
middleware sitting in front of a group of routes rather than being repeated
inside each controller.

## Forms

Every create/update form (`LoginForm`, `SignupForm`, `PostForm`,
`CommunityForm`, `CommentForm`) follows the same shape: local state for the
DTO being edited, a `validate<X>` function producing a per-field error map
plus a validity boolean, and a submit handler that calls the feature's
`api.ts` function inside a try/catch, surfacing a thrown error's message
above the fields. No form library is used — validation and submission are
explicit, which keeps the mechanism visible at the cost of some repetition
across forms (a candidate for a shared hook once the pattern stabilizes
further).

## Shared UI primitives

A small reusable kit — `Button`, `FormField`, `TextField`, `Composer`
(textarea + inline submit, used for comment authoring), `DropdownMenu`
(generic label→handler menu), `KebabMenu` (ellipsis-trigger wrapper around
`DropdownMenu`) — is composed across features rather than each feature
rolling its own inputs/menus. `DropdownMenu`'s open/close behavior follows a
standard close-on-outside-click pattern (a `ref` on the trigger container
plus a document-level `mousedown` listener while open), applied consistently
everywhere it's used.

## Styling

Tailwind CSS utility classes throughout — no component-level stylesheets or
CSS-in-JS — keeping styling co-located with markup and consistent with the
project's overall "explicit over implicit" tooling choices (see
`00-project-setup.md`).

## Future Plans

- **A shared data-fetching abstraction** (React Query/SWR, or a lightweight
  in-house `useAsyncResource`) to replace the repeated `{loading, error,
  data}` + `useEffect` hooks with one implementation that adds caching,
  request de-duplication, and retry — currently each hook re-solves the same
  problem independently.
- **A CI type-check gate** (`tsc --noEmit`) ahead of merge, so a type-level
  regression is caught before it reaches `main` rather than only surfacing on
  someone's next full local build.
- **Extend the existing ownership-gating pattern to posts.** Communities and
  comments already gate their owner-only actions (update/delete) behind an
  `ownerId === currentUser.id` check before rendering the controls; applying
  the same pattern to posts closes the one place it's not yet consistent.
- **Finish comment editing.** Comments currently support create and delete;
  the update path exists in the type layer (`CommentForm`'s `mode` prop) but
  isn't wired end-to-end yet.
- **Normalize the no-op-update contract.** A `PATCH` that changes nothing
  responds `204 No Content` by backend convention (see
  `02.backend_architecture.md`) — worth making every update wrapper treat
  that uniformly as "nothing to save" rather than each handling it slightly
  differently.
- **Externalize the API base URL** into an env variable, matching the same
  goal already tracked on the backend side (`00-project-setup.md`).
- **A shared `LoadingState`/`ErrorState` component** to replace the ad hoc
  per-page loading/error placeholders.
- **An edit-profile page**, completing the user-management flow the API
  already supports.
