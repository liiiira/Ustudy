# 01 — Database Design

## Model

PostgreSQL as the system of record. The domain maps cleanly onto a relational
model: `users`, `communities`, `posts`, `comments`, `community_enrollments`,
and `refresh_tokens`, related through foreign keys. Referential integrity
(a comment cannot outlive its post, a post cannot outlive its owning user)
is enforced at the database level via FK constraints rather than assumed and
re-checked in application code — the database is the last line of defense
against orphaned rows, not the only one (see `02.backend_architecture.md` for
the application-level existence checks that run before those constraints are
even reached).

`community_enrollments` is a join table resolving the many-to-many
relationship between `users` and `communities` (a user can join many
communities; a community has many members) — modeled as its own relation
rather than an array/JSON column, so membership stays queryable and
constrainable (e.g. uniqueness of a `(user_id, community_id)` pair) the same
way any other entity is.

## Schema evolution: forward-only migrations

Schema changes are expressed as an ordered, append-only sequence of migration
files rather than hand-edited in place:

```
001 add users
002 add communities
003 add posts
004 add comments
005 add community_enrollments
006 add refresh_tokens
007 make user unique in refresh_tokens
008 add community description
009 modify post table
010 add uuid generator to comments id
```

This treats schema state the way an event log treats application state: the
current schema is a *derived* value (replay all migrations against an empty
database), never edited directly. It gives every environment (local, test, CI
later, production later) a reproducible path to the same schema, and gives the
schema itself a history — migration `007` and `009` exist because an earlier
design decision (multi-row refresh tokens, an earlier post shape) turned out
to be wrong, and the fix is a visible, reviewable diff instead of a silent
edit to migration `001`.

## Future Plans

- **Keep the schema diagram alive.** This document referenced a schema image
  that no longer exists in the repo — a stale diagram is worse than no
  diagram. The planned `docs/DB.schema.md` should hold the actual current
  schema (tables, columns, constraints) as text, regenerated/updated whenever
  a migration lands, rather than a point-in-time image that silently rots.
- **Indexing strategy.** No documented indexes beyond primary keys and
  whatever unique constraints migrations added incidentally (e.g. the
  `refresh_tokens.user_id` uniqueness from migration `007`). Foreign key
  columns used in frequent joins/filters (`posts.community_id`,
  `comments.post_id`, `comments.owner_id`) are candidates once query patterns
  are known — indexing ahead of an actual access pattern is premature, but the
  access patterns exist today and haven't been reviewed for it.
- **`ON DELETE` semantics.** The cascade behavior for FK constraints (what
  happens to a post's comments when the post is deleted — cascade, restrict,
  or set null) isn't documented anywhere migrations aren't themselves the only
  source of truth for. Worth stating explicitly per relationship rather than
  leaving it implicit in whichever default Postgres/the migration used.
- **Soft delete vs. hard delete.** Deletes are currently hard deletes
  (`DELETE FROM ... RETURNING id`). Whether any entity (user accounts,
  especially, once other users' posts/comments reference them) should be
  soft-deleted instead is an open question with real referential-integrity
  consequences.
- **Migration rollback path.** Migrations are forward-only by design, but
  there's no documented/tested `down` path for rolling a bad migration back in
  a running environment — only mentioned here as a gap, not a suggestion to
  abandon the forward-only strategy.
- **Seed data.** No fixture/seed script for local development — every local
  environment starts from an empty schema.
