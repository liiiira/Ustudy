# 02 — Backend Architecture

## Layering

The backend is organized as a classic layered architecture with a strict,
unidirectional dependency graph — each layer depends only on the layer
beneath it, never the reverse, and never skips a layer:

```
HTTP Request
     │
     ▼
Middleware        (Chain of Responsibility: validation, auth, error handling)
     │
     ▼
Controller        (HTTP adapter — req/res only)
     │
     ▼
Service           (business rules, invariants, orchestration)
     │
     ▼
Repository        (data access — parameterized SQL, no business logic)
     │
     ▼
PostgreSQL
```

| Layer | Responsibility | Must not do |
|---|---|---|
| Middleware | Cross-cutting, request-scoped concerns | Contain feature-specific business logic |
| Controller | Translate HTTP ↔ domain calls; shape the response envelope | Contain business rules or SQL |
| Service | Enforce invariants, orchestrate repositories, own error semantics | Know about `req`/`res` or HTTP status codes as *decisions* (it throws a typed error; the HTTP mapping happens elsewhere) |
| Repository | Data access — one method per query, parameterized, mapped to DTOs | Enforce business rules (e.g. "is this email already taken" is a service concern, not a `WHERE` clause) |

This is a straightforward application of **separation of concerns** and the
**Single Responsibility Principle** at the module level: each layer has one
reason to change. A new validation rule touches middleware/schemas; a new
business rule touches a service; a new query touches a repository — changes
stay localized instead of rippling across the stack.

## Repository layer: a data-mapper without an ORM

Repositories are a **data-mapper**-style abstraction (Fowler): thin functions
that translate between SQL result rows and plain TypeScript DTOs
(`snake_case` columns aliased to `camelCase` fields), with no ORM in between.
The `pg` connection pool is used directly, which trades away
query-builder/relation-loading convenience for full control over the SQL that
runs — a deliberate tradeoff, not an oversight (see the root `README.md`).

Note this is **not** an Active Record pattern and **not** a rich domain
model — a `User`/`Post`/`Comment` is a plain data structure with no behavior
of its own; all behavior lives in the service layer as free functions that
operate *on* that data. This is closer to an **anemic domain model**, which is
a reasonable tradeoff for CRUD-shaped features with modest business logic —
worth naming explicitly as a decision, since it stops being a good fit the
moment feature logic grows richer invariants than "a couple of uniqueness
checks and an ownership comparison."

## Service layer: where invariants live

The service layer is where domain rules are enforced before a repository
call — e.g., "an email must be unique" or "only the owning user can update a
post" (an authorization invariant, not just a data constraint). Services
compose repositories and, for rules that span feature boundaries, other
services (`auth.service` depends on `user.service`; `post.service` depends on
`community.service`) — always through the sibling's *service* layer, never
reaching past it into that feature's repository, so an invariant defined once
in a service can't be silently bypassed by a peer feature.

Errors are represented as a single typed exception (`AppError`, carrying an
HTTP status code and message) rather than ad hoc throw sites — this is what
lets the error-handling middleware stay a single, generic catch-all instead of
each controller needing its own try/catch-and-translate logic.

## Middleware chain

Express's middleware chain is a direct instance of the **Chain of
Responsibility** pattern: each middleware either handles the request, passes
it on (`next()`), or short-circuits with an error. Validation
(`validateBody`/`validateParams`, zod-schema-driven), authentication
(`isAuthenticated`, JWT verification), and error handling are all implemented
as links in that chain rather than inline checks duplicated per controller.

Because Express's own contract doesn't forward rejected promises out of an
`async` handler into the error-handling chain, controllers are wrapped by
`asyncWrapper` — a higher-order function (decorator) that catches a rejected
promise and forwards it to `next(err)`, bridging async/await onto Express's
synchronous error-propagation model. This is worth naming as a pattern
(decorator over a handler) rather than boilerplate, since it's the mechanism
that keeps every controller able to just `throw` instead of manually
try/catching.

## Future Plans

- **Dependency inversion at the repository boundary.** Services currently
  import repository modules directly (`import * as userRepository from
  "./user.repository"`), coupling them to a concrete module rather than an
  interface. This is fine at the current scale, but it means unit-testing a
  service in isolation requires module-level mocking rather than injecting a
  fake/stub implementation — introducing a repository interface (even a
  lightweight one) and injecting the concrete implementation would decouple
  service tests from the real `pg` pool.
- **Deduplicate the dynamic `UPDATE` builder.** The "build a `SET` clause from
  whichever fields are present" logic is hand-written, nearly identically,
  in the users, posts, and comments repositories. A small shared helper would
  remove that duplication without introducing a query builder.
- **Formalize per-layer DTOs.** Repository return types, service input types,
  and controller request/response shapes currently share the same interfaces
  in most features (e.g. `User` used across all three layers). Distinguishing
  a repository-facing DTO from an API-facing response shape would make it
  possible to change one without silently changing the other's contract.
- **Structured error logging.** `errorMiddleware` currently does
  `console.error(err)` — no correlation ID, no structured fields (route,
  method, user id), which will matter the moment there's more than one
  instance of the API running.
- **Formal authorization layer.** Ownership checks (`userId !==
  record.ownerId`) are currently hand-written per service method rather than
  expressed as a reusable authorization policy — worth a shared abstraction
  once a second permission model (e.g. roles, community-moderator
  permissions) is introduced.
