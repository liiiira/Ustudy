# 03 — Backend Architecture

As the backend grew, I wanted to keep different responsibilities separated instead of putting database queries, business logic, and HTTP handling in the same place.

The backend follows a layered architecture with **controllers, services, repositories, and middlewares**.

## Architecture

```text
                  HTTP Request
                       │
                       ▼
                ┌──────────────┐
                │  Middleware  │
                │ Validation   │
                │ Error Handle │
                └──────┬───────┘
                       │
                       ▼
                ┌──────────────┐
                │  Controller  │
                │ HTTP layer   │
                └──────┬───────┘
                       │
                       ▼
                ┌──────────────┐
                │   Service    │
                │ Business     │
                │ Logic        │
                └──────┬───────┘
                       │
                       ▼
                ┌──────────────┐
                │ Repository   │
                │ Database     │
                │ Access       │
                └──────┬───────┘
                       │
                       ▼
                  PostgreSQL
```

## Repository

The **repository layer** is responsible for interacting with the database.

It contains the database queries and operations needed by the application. (create, find, update, delete)

For example:

```ts
userRepository.findById(id)
userRepository.create(data)
userRepository.updateById(id, data)
userRepository.deleteById(id)
```

The repository focuses only on **data access**. 
It does not contain application business rules.

---

## Service

The **service layer** contains the application's business logic.
It uses repositories to access data and decides what should happen according to the application's rules.
It also handles errors by throwing ` class AppError` objects containing the appropriate http code and error message.

For example, a service might:

* Check whether a user exists
* Check whether an email is used
* Call the repository to update the user

The service doesn't not deal directly with HTTP concepts such as `req` and `res`.

---

## Controller

The **controller layer** handles HTTP requests and responses.

Its main responsibilities are:

* Reading parameters, body, and query data
* Calling the appropriate service
* Returning the HTTP response

Controllers are kept relatively thin because the actual business logic belongs in the service layer.

```text
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

---

## Middlewares

Middlewares handle concerns that are shared across different routes.

Examples include:

* Request validation
* Authentication
* Authorization
* Error handling

For example, a validation middleware can validate the request body before it reaches the controller.

```text
Request
   ↓
Validation Middleware
   ↓
Controller
   ↓
Service
```

Error handling is also centralized in an error middleware, allowing errors from controllers and services to be handled consistently.

---

## Separation of Responsibilities

The main idea is to keep each layer focused on one responsibility:

| Layer      | Responsibility         |
| ---------- | ---------------------- |
| Middleware | Request-level concerns |
| Controller | HTTP handling          |
| Service    | Business logic         |
| Repository | Database access        |
| Database   | Data persistence       |

This separation makes the backend easier to understand, test, and maintain as the project grows.
