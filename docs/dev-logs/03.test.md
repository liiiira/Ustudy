# 03 — Testing

## Strategy: black-box integration tests over the HTTP boundary

Tests are written against the running Express app through Supertest, not
against controllers/services/repositories in isolation:

```ts
const response = await request(app)
  .post("/api/v1/users")
  .send({ username: "kira", password: "12345678", email: "kira@gmail.com" });

expect(response.status).toBe(201);
```

Vitest supplies the runner, assertions, and lifecycle hooks; Supertest issues
real HTTP requests at the app instance. Each test therefore exercises the full
request path — middleware, controller, service, repository, and a real
Postgres instance — rather than a single unit with its collaborators mocked
out. This is deliberately a **black-box** test: assertions are made on the
observable HTTP contract (status code, response shape), not on internal
call sequences.

## Test isolation

A dedicated test environment keeps this from colliding with local development
state:

- A separate `postgres-test` container (`docker-compose.test.yml`), distinct
  from the development database.
- A dedicated `.env.test` configuration, loaded when `NODE_ENV=test`.
- `test.sh` orchestrates the full cycle: bring the test containers up, run
  migrations against the test database, then run the suite — so `pnpm test`
  is a single reproducible entry point rather than a manual multi-step
  checklist.

## What this buys, and what it costs

Testing at the HTTP boundary means a test verifies that the layers integrate
correctly, not just that each one is individually correct — it would catch,
for instance, a controller passing arguments to a service in the wrong order,
which a mocked-service unit test on the controller alone would miss. The cost
is the inverse of a unit test's usual tradeoff: every test pays for a real
database round-trip, and a failure only says "the request path is broken
somewhere," not which layer.

Right now the suite sits at one point on the **test pyramid** — all
integration, no unit layer underneath it — rather than a deliberate blend.
That's a reasonable starting point for a project this size, but it's worth
naming as a gap, not a finished strategy.

## Future Plans

- **A unit-test layer under the integration tests.** Service-level business
  rules (uniqueness checks, ownership comparisons, the "nothing changed →
  return null" convention) currently have no test that isolates them from a
  real database — every path to them goes through an HTTP call and a live
  repository. Unit tests against services with a fake/stub repository
  (enabled by the dependency-inversion gap noted in
  `02.backend_architecture.md`) would let business-rule regressions be caught
  without a database round trip, and would pinpoint the failing layer
  directly instead of just "the request failed."
- **Negative-path and authorization coverage.** The example shown here is a
  happy-path create; coverage of `401`/`403`/`404` branches (wrong owner,
  missing resource, missing/expired token) isn't visible from this doc and is
  worth confirming exists per feature, especially given the auth gaps flagged
  in `04.user.md`.
- **Test data builders/factories.** Test fixtures are currently inline object
  literals repeated per test file; a shared builder (e.g. `buildUser({...})`
  with sensible defaults) would reduce duplication and make intent-relevant
  fields stand out in each test.
- **Coverage reporting.** No coverage threshold/report is wired into
  `pnpm test` — there's currently no signal for which branches (especially
  error branches) are untested.
- **CI execution.** The suite currently only runs locally; wiring `test.sh`
  into a CI pipeline on push/PR is the natural next step once one exists.
