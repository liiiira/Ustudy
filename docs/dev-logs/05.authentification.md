# 4. Authentication

## Overview

Implemented a stateless, bearer-token authentication system from scratch (no third-party identity provider such as Auth0 or Firebase Auth), following the classic **access token / refresh token** pattern used in OAuth2-inspired architectures. The goal was to keep the API stateless on a per-request basis while still allowing server-side session control (revocation) through the refresh token.

## Token Model

| Token | Lifetime | Purpose | Transport |
|---|---|---|---|
| Access Token | 15 minutes | Authorizes requests to protected endpoints | `Authorization: Bearer <token>` header, attached per request |
| Refresh Token | 7 days | Used exclusively to mint new access tokens | Sent to a dedicated `/refresh` endpoint |

The short-lived access token limits the exposure window if it is ever leaked (e.g. via XSS), while the longer-lived refresh token allows the user to stay logged in without re-entering credentials, at the cost of needing a server-side revocation mechanism.

## Backend

- **Protected routes** are guarded by a `isAuthenticated` middleware that validates the `Authorization: Bearer <token>` header, checks the JWT signature and expiration, and attaches the decoded user identity to the request context.
- **`/refresh` endpoint**: validates the incoming refresh token against its record in the database (existence + revocation status + expiration), and if valid, issues a new access token. This decouples "is this refresh token still valid" (a DB lookup, revocable) from "is this access token still valid" (a pure JWT signature/expiry check, non-revocable by design).
- **Logout**: revokes the refresh token by invalidating its database record. Since access tokens are not individually revocable (stateless JWTs), revocation happens at the refresh-token layer — logout guarantees the session cannot be *renewed* past the current access token's remaining lifetime (≤ 15 min).
- **Current session model**: one refresh token per user (1:1), not yet per device. This is a deliberate MVP simplification — logging in elsewhere effectively invalidates the previous session's ability to refresh.

## Frontend

- **`token.ts`** centralizes access token storage behind explicit `get`/`set` functions rather than exposing a shared mutable variable across the codebase. The `authApi` layer is the sole consumer, which keeps the token's lifecycle in one place and makes it easy to swap the storage strategy later without touching call sites.
- **Automatic refresh on 401**: the API layer intercepts `401 Unauthorized` responses, transparently calls `/refresh` to obtain a new access token, and retries the original request. If the refresh itself fails (expired/revoked refresh token), the user is logged out client-side.
- **`AuthContext`** (React Context API) exposes `isAuthenticated`, `loading`, and `login` / `logout` functions to the component tree, centralizing auth state instead of prop-drilling or duplicating checks per component.
- **`ProtectedRoute`** wraps routes that require authentication: it reads `isAuthenticated` from `AuthContext` and redirects unauthenticated users to `/login` using `navigate(..., { replace: true })`, so the protected route isn't left in the browser history (preventing back-navigation into a stale protected view after redirect).

## Request Lifecycle (summary)

1. Login → server issues access token + refresh token (refresh token persisted server-side).
2. Client stores the access token via `token.ts`; subsequent requests attach it as a bearer token.
3. Access token expires (15 min) → next request returns `401`.
4. Client calls `/refresh` → server validates the refresh token against the DB → issues a new access token → original request is retried.
5. Logout → refresh token is revoked in the database → client clears local auth state.

## Current Limitations

- Single refresh token per user means no true multi-device session support: a new login can effectively displace an existing session's ability to refresh.
- No email verification at registration yet, so account creation is not yet gated by ownership of the email address.

## Planned Improvements

- **Per (user, device) refresh tokens**: move from a single refresh token per user to one per device/session, enabling concurrent multi-device logins and *selective* revocation (e.g. "log out this device" without affecting others). This also opens the door to refresh token rotation with reuse detection — flagging a token as compromised if a revoked/rotated token is presented again.
- **Email verification**: send a verification code on registration and gate full account activation on its confirmation.
- **OAuth2 social login**: add "Sign in with Google" (and similar providers) via the OAuth2/OIDC authorization code flow, issuing Ustudy's own access/refresh tokens once the provider identity is verified.
